# Зачем нужен DCC-MCP

## Что такое DCC-MCP?

DCC-MCP – это набор инструментов с открытым исходным кодом, который позволяет связывать AI-ассистентов с творческими программами. AI-ассистенты представляют собой программы, которые могут вызывать другие программы для выполнения определенных задач. DCC означает создание цифрового контента; к приложениям DCC относятся Maya, Blender, Houdini и Photoshop.

Агенты и системы автоматизации могут использовать эти инструменты для моделирования, работы с материалами, создания анимации и процессов рендеринга. Инструменты имеют определенные параметры, их типы, а также результаты их работы. Таким образом, можно проверить и утвердить результаты работы этих инструментов.

MCP (Model Context Protocol), REST APIs и `dcc-mcp-cli` обеспечивают совместное использование инструментов для обнаружения контекста моделей, проверки информации, выбора подходящих экземпляров, регулирования правил безопасности и проверки результатов. Основа данной инфраструктуры позволяет использовать эти инструменты совместно; адаптеры соединяют различные приложения, а Skills предоставляют рекомендации по использованию рабочих процессов.

DCC-MCP возник в результате работы над адаптерами для реальных DCC-приложений. Проблемы, связанные с привязкой потоков к конкретным экземплярам программы, процессом выбора экземпляров, жизненным циклом объектов, процессом обнаружения проблем и диагностики, постоянно возникали на разных хостах. Мы добавили возможность использования общих контрактов только после того, как эти проблемы снова возникли.

## Начнем с процесса производства.

Агент использует процесс, который ему предоставлен. Он не определяет этот процесс для команды.

> Стандартизировать производство → превратить стандарты в рабочие процессы → упаковать эти рабочие процессы в вид инструментов → позволить агентам использовать эти инструменты для выполнения своих обязанностей.

Необходимо определить критерии именования, входных данных, выходных результатов, проверок, право собственности на процесс и условия его приема. Затем необходимо соединить все эти элементы в одно повторяемое рабочее процесс. После этого этот процесс можно использовать как типичный инструмент. Тот же самый инструмент может использоваться людьми, скриптами, CI-системами или агентами.

## Почему прямые сценарии перестали развиваться?

Попросить модель написать и запустить скрипт на языке `mayapy`, `hython` или Blender Python является полезным для исследований. Повторяющаяся производственная работа выявила следующие ограничения:

- Эта модель снова генерирует аналогичный код на каждом ходе, при этом результат может варьироваться.
- APIы DCC часто требуют выполнения операций в основном потоке выполнения программы, а также проверок на готовность приложения к выполнению определенных действий.
- Некоторые открытые сцены или приложения могут создавать неоднозначность в отношении целевой области выполнения задачи.
- Длинные операции требуют прогресса, прекращения действий в определенных моментах, создания пунктов остановки и восстановления ситуации после окончания операции.
- Успешное завершение процесса не доказывает того, что изменения произошли в желаемой сцене или документе.
- Невозможно воспроизвести ошибки без использования вводимых данных, идентификаторов запросов, журналов действий и других необходимых данных.

Эти проблемы возникали на всех адаптерах. Следовательно, они должны были находиться в общей инфраструктуре.

## Проблемы и контракты, связанные с ними

| Повторяющаяся проблема | Что мы узнали | Ответ DCC-MCP |
| --- | --- | --- |
| В каждом ходе модели переписывают логику выполнения задачи. | Знания, полученные в процессе работы с пайплайном, должны сохраняться независимо от изменений моделей и инструкций. | Навыки, оформленные в виде версионных схем, с использованием типизированных шаблонов, процедур валидации и ресурсов для повторного использования. |
| Каждый адаптер пересобирает код, отвечающий за транспорт и жизненный цикл объекта. | Интеграции с хостами требуют наличия общего контракта. | Основная часть выполнения задач, Gateway, командный интерфейс и адаптеры, принадлежащие самому хосту. |
| APIы DCC имеют ограничения, связанные с количеством потоков и степенью готовности системы к выполнению задач. | Общие процедуры выполнения задач недостаточны. | Организация распределения основных потоков, готовность к выполнению задач, маршрутизация экземпляров и выполнение задач на хостах. |
| Большие каталоги инструментов занимают много места и усложняют процесс выбора подходящего инструмента. | Агенты должны выявлять лишь то, что необходимо для выполнения задачи. | Прогрессивное исследование с помощью `search -> load/describe -> call`. |
| Творческие процессы могут происходить медленно или частично завершаться до конца. | Звонок должен иметь семантику жизненного цикла, а не просто значение возвращаемое при выполнении операции. | Асинхронные задачи, прогресс выполнения задач, отмена задач, точки контроля и передача обязанностей между участниками проекта. |
| Использование инструментов становится чем-то непонятным, как если бы это была „черная коробка“. | Команды по производству требуют доказательств, которые можно проверить. | Идентификаторы запросов, политика, записи аудита, логи, метрики, информация о состоянии системы, а также возможность повторного выполнения действий. |
| Существующие инструменты иногда не предоставляют каких-либо полезных API для использования. | Автоматизация пользовательского интерфейса является вариантом отступления, а не основой для работы с интерфейсом. | DCC-CUA / Управление интерфейсом, связанное с конкретной процессом и окном, с возможностью операций в определенной области, проверки политики, а также `snapshot -> find -> act -> wait -> verify` |
| Полезные рабочие процессы должны перемещаться между людьми и проектами. | Папка с скриптами не является способом распространения программ. | Пакеты для рынка, неизменные источники данных, возможность быстрой перезагрузки, а также ограничения, связанные с проектом или командой. |

## Кто владеет чем?

Система разделяет общие службы на отдельные функции, связанные с конкретным хостом.

| Слои | Ответственность |
| --- | --- |
| Интерфейс агента | Эндпункты типа MCP и REST, команды в CLI, схемы, ресурсы, подсказки и структурированные результаты. |
| Управляющая площадка | Обнаружение путей передачи данных, расчет маршрутов, проверка правил, управление жизненным циклом объектов, возможность наблюдения за процессами, а также использование множества экземпляров объектов. |
| Время выполнения задачи DCC: | Отправление основного потока, готовность к выполнению задач, отмена задач, точки контроля, а также выполнение операций без рисков для хоста. |
| Адаптер | Установка, совместимость, API-интерфейсы хоста, а также поведение приложений, которые являются собственностью каждого репозитория DCC. |
| Навыки | Проверяется знание процессов, аргументы, этапы процесса, а также правила, касающиеся проектов или команд. |

[Документация по основной архитектуре](https://dcc-mcp.github.io/dcc-mcp-core/guide/architecture) является источником информации для текущих контрактов. Вопросы, связанные с установкой программ на конкретных хостах, совместимость программ и решение возникающих проблем, остаются в соответствующих репозиториях.

## CLI, MCP и REST имеют одну и ту же реализацию.

Код общих сервисов, а также типовые REST/OpenAPI-контракты являются частью реализации. Данный код позволяет использовать инструмент `dcc-mcp-cli` для вызова REST API Gateway. Инструмент MCP имеет простую структуру: функции `search`, `describe`, `load_skill` и `call` предоставляют одинаковый функционал как для клиентов, использующих MCP, так и для других клиентов. Оба варианта использования используют одни и те же сервисы для обнаружения объектов, проверки данных, расстановки запросов и выполнения операций.

| Потребители | Предпочитаемая поверхность | Необходим агент искусственного интеллекта. |
| --- | --- | --- |
| Художники, операторы, скрипты shell и CI-системы | Типографский формат CLI или REST | Нет. |
| Автоматизация студий и создание пользовательских приложений | Отдыхаем, используя генерируемые клиенты OpenAPI. | Нет. |
| AI-IDE и помощники, предназначенные исключительно для работы с MCP-фреймворком | Минимальная рабочая процедура MCP | Да. |
| Умные процессы работы и оркестрирование данных в облаке | Интеграция с REST/OpenAPI; MCP при участии агента. | Нет. |

Пайплайн может напрямую использовать REST-интерфейс, создавать клиентские программы из файла `/v1/openapi.json`, или использовать CLI в процессе интеграции и обработки данных. Агент также может получить такие возможности через легкий интерфейс MCP.

Существующая сервисная функция OpenAPI 3.x также может использоваться в качестве инструментов MCP. Она остается обычной REST-сервисом, и не требует переработки с учетом аспектов искусственного интеллекта.

## Сначала используйте уже существующие протоколы.

MCP является стандартным входным пунктом для агентов в этой индустрии. Поэтому DCC-MCP использует его вместо использования собственного протокола. REST, Python, C++, HTTP, командные порты, нативные плагины и официальные инструменты производителей могут работать через один и тот же контрольный центр.

DCC-MCP не заменяет агента, API DCC или интеграцию с поставщиками услуг. Когда поставщик предоставляет нормальные нативные или официальные функции MCP, адаптер сохраняет свои названия и структуры данных. DCC-MCP обеспечивает общую систему для обнаружения объектов, маршрутизации, обеспечения безопасности, управления жизненным циклом объектов, их распределения и диагностики.

## Знания, связанные с процессами работы в магазине навыков.

“Skill” представляет собой протестированную рабочую процедуру в виде версионованного, типизированного и распространяемого наборов функций.

Граница владения следующая:

- Корпус и адаптеры обеспечивают поддержку связи, безопасность потоков, функции маршрутизации, настройки политики и возможности наблюдения за процессами.
- TDs и TAs позволяют сохранять информацию о названиях проектов, проверках сценариев, подготовке ресурсов, этапах публикации, правилах экспорта и процедурах обзора проекта в рамках уже существующей системы управления проектами.
- Агенты выбирают подходящий инструмент для выполнения задачи и используют проверенные способы решения проблемы, вместо того чтобы заново создавать весь процесс выполнения задачи.

Это позволяет избежать повторного генерирования одних и тех же кодов. Также это позволяет студии распределять различные возможности в зависимости от проекта, отдела или этапа производства, без необходимости изменения контрольной системы.

## Сохраняйте доказательства неудач.

Диагностика начинается с использования значения `request_id`, типа инструментов и аргументов, выбранной экземпляра DCC, а также наблюдаемых результатов. Gateway и CLI предоставляют информацию о состоянии системы, логах, статистике и структурированных данных.

Это создает конкретный цикл:

1. Производить отказ на реальном хосте;
2. Необходимо определить, является ли этот элемент частью Core, адаптера или самостоятельным компонентом.
3. Приведем минимальное исправление в этой границе.
4. Повторно валидируют ту же самую вызывку.
5. Необходимо сохранять доказательства, чтобы следующие улучшения основывались на реальных данных, а не на догадках.

## Известные ограничения

DCC-MCP не утверждает, что каждое творческое применение будет одинаковым.

- Нативные навыки и API все еще предпочтительнее, чем DCC-CUA/UI Control. В первом случае необходимо связать определенный процесс с конкретным окном программы.
- Коре не имеет специфических семантических особенностей, связанных с конкретными хостами.
- Адаптер не может гарантировать безопасный возврат к предыдущему состоянию, если хост не предоставляет каких-либо API для управления транзакциями.
- Пакеты для рынка дополняют основную структуру системы; они не скрывают недостатки в самом Core или адаптере.
- Этот проект предоставляет инфраструктуру для агентов. Он не определяет, какой именно агент или модель следует использовать.

## Что все еще зависит от человеческого суждения…

Многие производственные задачи можно стандартизировать, проверить их качество и автоматизировать. Однако такие аспекты, как эстетический вкус, художественное оформление, композиция, темп исполнения и стиль исполнения, все же сложно описать в виде стабильных условий. DCC-MCP не утверждает, что сама инфраструктура может решить все эти проблемы.

DCC-MCP обрабатывает те этапы процесса, которые можно повторять снова и снова. Агентам предоставляется контролируемый доступ к соответствующим инструментам. Лучшее понимание ситуации, умение применять различные методы рассуждений и творческое мышление позволяют использовать те же самые инструменты, без необходимости повторного создания всех интеграций DCC.
