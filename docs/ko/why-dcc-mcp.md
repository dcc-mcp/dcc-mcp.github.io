# DCC-MCP의 설계 원리

## DCC-MCP란 무엇인가요?

DCC-MCP는 AI 에이전트를 창의적인 소프트웨어와 연결하는 오픈소스 도구입니다. AI 에이전트란, 특정 작업을 수행하기 위해 다양한 도구들을 호출할 수 있는 AI 어시스턴트입니다. DCC는 디지털 콘텐츠 제작을 의미합니다. 사용되는 애플리케이션으로는 Maya, Blender, Houdini, Photoshop 등이 있습니다.

에이전트와 자동화 시스템은 이러한 도구들을 사용하여 모델링, 재료 처리, 애니메이션, 렌더링 등의 작업을 수행할 수 있습니다. 입력된 도구는 자신이 사용하는 매개변수들, 그 매개변수들의 종류, 그리고 그 결과를 정의합니다. 이렇게 하면 해당 작업의 결과를 검토하고 검증할 수 있습니다.

MCP(모델 컨텍스트 프로토콜), REST API, 그리고 `dcc-mcp-cli`는 도구 발견, 유효성 검증, 인스턴스 선택, 보안 정책, 결과 확인 등의 기능을 공유합니다. Core는 이러한 공유된 인프라를 제공하며, 어댑터들은 각 애플리케이션을 연결해줍니다. Skills는 재사용 가능한 워크플로우 가이드를 제공합니다.

DCC-MCP는 실제 DCC 애플리케이션에서의 어댑터 작업을 통해 개발되었습니다. 스레드 친화성, 인스턴스 선택, 라이프사이클 관리, 디스커버리 및 진단 기능 등은 여러 호스트에서 반복적으로 발생하는 문제들이 있었습니다. 이러한 문제들이 계속 발생하자, 우리는 공유된 컨트랙트를 추가하기로 결정했습니다.

## 생산 과정부터 시작해보세요.

에이전트는 자신에게 주어진 프로세스를 사용합니다. 하지만 그 프로세스를 팀에게 정의하지는 않습니다.

> 생산 과정을 표준화한다 → 표준들을 작업 흐름으로 전환한다 → 작업 흐름을 도구로 패키징한다 → 에이전트들이 해당 도구를 사용할 수 있도록 한다.

명명법, 입력값, 출력값, 검사항목, 소유권, 그리고 수용 기준을 정의합니다. 이를 모두 하나의 반복 가능한 작업 흐름으로 연결시킨 다음, 그 작업 흐름을 특정한 형태로 제공합니다. 이 도구는 사람들, 스크립트, CI 시스템, 또는 에이전트 등 다양한 방법으로 호출될 수 있습니다.

## 왜 직접 작성된 스크립트는 확장성을 유지할 수 없는가?

모델에게 `mayapy`, `hython`, 또는 Blender Python 스크립트를 작성하고 실행하도록 요청하는 것은 탐구를 위해 유용합니다. 반복적인 생산 작업을 통해 다음과 같은 한계들이 드러났습니다:

- 이 모델은 매 턴마다 유사한 코드를 생성하지만, 그 결과는 항상 다릅니다.
- DCC API들은 대개 메인 스레드에서 실행되어야 하며, 애플리케이션에 특화된 준비 상태 확인도 필요합니다.
- 여러 개의 열린 장면이나 애플리케이션 인스턴스가 존재하기 때문에, 실행 대상이 불분명해집니다.
- 긴 작업들은 진행 과정, 중단, 검토, 그리고 복구가 필요합니다.
- 성공적인 프로세스 종료가 반드시 원하는 장면이나 문서가 변경된다는 것을 의미하지는 않습니다.
- 실패 사항들을 재현하는 것은, 입력된 데이터나 요청 ID, 로그 정보, 추적 정보 없이는 어렵습니다.

이러한 문제들은 모든 어댑터에서 발생했기 때문에, 이는 공유 인프라에 속하는 문제들이었습니다.

## 문제들과 그로 인해 발생하는 계약들

| 반복되는 문제들 | 우리가 배운 것들 | DCC-MCP 응답 |
| --- | --- | --- |
| 모델들은 각 턴마다 로직을 다시 작성합니다. | 파이프라인에 대한 지식은, 모델이나 프롬프트가 변경하더라도 그대로 유지되어야 합니다. | 버전 관리가 가능한 기술들로, 타이핑된 스키마와 유효성 검증 기능이 포함되어 있으며, 재사용 가능한 도구들도 제공됩니다. |
| 모든 어댑터는 전송 및 라이프사이클 코드를 다시 생성합니다. | 호스트 통합에는 공통된 계약이 필요합니다. | 코어 런타임, 게이트웨이, CLI, 그리고 얇은 호스트가 소유하는 어댑터들 |
| DCC API들은 스레드 및 준비 상태와 관련된 제약 조건들을 가지고 있습니다. | 일반적인 프로세스 실행만으로는 충분하지 않습니다. | 메인 스레드의 전송, 준비 상태, 인스턴스의 라우팅, 그리고 호스트의 실행 관련 기능들 |
| 대규모 도구 카탈로그는 많은 공간을 차지하며, 사용자가 원하는 도구를 선택하는 것을 어렵게 만듭니다. | 에이전트는, 업무가 필요로 하는 정보만을 파악해야 합니다. | `search -> load/describe -> call` |
| 창의적인 작업은 느리게 진행될 수도 있고, 일부만 완료될 수도 있습니다. | 호출에는 라이프사이클 관련 semantics가 필요합니다. 단순히 반환값만 있어서는 안 됩니다. | 비동기적인 작업들, 진행 상황, 취소 처리, 체크포인트, 그리고 아트리뷰스 핸드오프 |
| 도구 사용은 마치 블랙박스와 같은 것입니다. | 제작팀은 자신들이 확인할 수 있는 증거가 필요합니다. | 요청 ID, 정책, 감사 기록, 로그, 추적 데이터, 메트릭스, 상태 정보, 그리고 재생 데이터 |
| 기존의 도구들 중에는, 사용할 수 있는 API가 전혀 없는 경우도 있습니다. | UI 자동화는 보조적인 방법일 뿐, 기반이 되는 방법은 아닙니다. | DCC-CUA / 정확한 프로세스와 창에 바인딩된 UI 컨트롤로, 범위 설정된 작업, 정책 검사, 그리고 `snapshot -> find -> act -> wait -> verify` 기능을 제공합니다. |
| 유용한 작업 흐름은 사람들과 프로젝트 사이를 자유롭게 이동해야 합니다. | 스크립트 폴더는 배포 모델이 아닙니다. | 마켓플레이스 패키지, 불변의 소스 참조, 핫리로드 기능, 프로젝트/팀 범위 등 |

## 누가 무엇을 소유하고 있는가?

이 시스템은 공유 서비스와 호스트에 특화된 행동을 분리합니다.

| 레이어 | 책임 |
| --- | --- |
| 에이전트 인터페이스 | MCP와 REST 엔드포인트, CLI 명령어, 스키마, 리소스, 프롬프트, 그리고 구조화된 결과들입니다. |
| 제어 플레인 | 게이트웨이의 발견, 라우팅, 정책 검증, 라이프사이클 관리, 관찰 가능성, 그리고 여러 인스턴스 간의 연동 기능 |
| DCC 실행 시간 | 메인 스레드의 전송, 준비 상태, 작업의 실행, 취소, 체크포인트, 그리고 호스트가 안전하게 실행할 수 있도록 하는 기능들입니다. |
| 어댑터 | 각 DCC 리포지토에 속하는 설치, 호환성, 호스트 API들, 그리고 애플리케이션별 특성들. |
| 스킬 | 워크플로우에 관한 지식, 논리적인 주장, 워크플로우의 각 단계, 그리고 프로젝트나 팀의 규칙들을 검증합니다. |

[핵심 아키텍처 문서](https://dcc-mcp.github.io/dcc-mcp-core/guide/architecture)는 현재의 계약들에 대한 정확한 정보를 제공하는 자료입니다. 호스트별 설치 방법, 호환성, 문제 해결 방법 등은 각 어댑터 리포지토리에 남아 있습니다.

## CLI, MCP, 그리고 REST는 모두 같은 구현 방식을 사용합니다.

공유된 서비스 코드와 입력된 REST/OpenAPI 컨트랙트가 바로 구현 방식입니다. `dcc-mcp-cli`는 Gateway의 REST API를 호출합니다. MCP는 간단한 구조를 가지고 있습니다: `search`, `describe`, `load_skill`, `call`과 같은 기능들은 MCP 전용 클라이언트에게도 동일한 작업 흐름을 제공합니다. 두 방식 모두 동일한 발견, 유효성 검사, 라우팅, 정책 및 호출 서비스를 사용합니다.

| 소비자 | 가장 적합한 표면 | AI 에이전트가 필요합니다. |
| --- | --- | --- |
| 예술가들, 테스터들, 운영자들, 쉘 스크립트들, 그리고 CI | 타이프된 CLI 또는 REST | 아니요. |
| 스튜디오 자동화 및 맞춤형 애플리케이션 | 생성된 OpenAPI 클라이언트와 함께 휴식을 취합니다. | 아니요. |
| MCP만을 사용하는 AI IDE와 도우미들 | 최소한의 MCP 워크플로우 | 네. |
| 스마트 워크플로우 캔버스와 클라우드 오케스트레이션 | REST/OpenAPI 통합 기능이 있으며, 에이전트가 참여할 경우 MCP 기능도 활용할 수 있습니다. | 아니요. |

파이프라인은 직접 REST를 호출할 수도 있고, `/v1/openapi.json`에서 클라이언트를 생성할 수도 있습니다. 또한, CI 및 운영 과정에서 CLI를 사용할 수도 있습니다. 에이전트는 얇은 MCP 인터페이스를 통해 동일한 기능을 수행할 수 있습니다.

기존의 OpenAPI 3.x 서비스도 MCP 도구로 활용될 수 있습니다. 이 서비스는 여전히 일반적인 REST 서비스로 남아 있으며, AI를 기반으로 재구성할 필요가 없습니다.

## 먼저, 이미 존재하는 프로토콜들을 사용해보세요.

MCP는 업계 표준의 에이전트 진입점이므로, DCC-MCP는 별도의 프라이빗 프로토콜을 만들어내는 대신, MCP를 사용합니다. REST, Python, C++, HTTP, 명령 포트, 네이티브 플러그인, 그리고 공식적인 벤더 도구들도 같은 제어 플레인 뒤에서 작동할 수 있습니다.

DCC-MCP는 에이전트나 DCC API, 또는 공급업체의 통합 기능을 대체하지 않습니다. 공급업체가 사용 가능한 네이티브 또는 공식적인 MCP 기능을 제공할 경우, 어댑터는 그 이름과 스키마를 그대로 유지합니다. DCC-MCP는 이러한 기능들을 위한 공유된 발견, 라우팅, 안전성, 라이프사이클 관리, 배포 및 진단 기능을 제공합니다.

## 스킬 스토어의 작업 흐름 관련 지식

“Skill”은 테스트된 워크플로우를 버전 관리가 가능하고, 텍스트로 표현될 수 있으며, 배포가 가능한 형태로 패키징하는 기능입니다.

소유권의 경계는 다음과 같습니다:

- 코어와 어댑터는 연결성, 스레드 안전성, 라우팅, 정책 설정, 그리고 관찰 가능성과 관련된 기능들을 담당합니다.
- TDs와 TAs는 프로젝트의 이름 지정, 장면 검사, 자산 준비, 게시 단계, 내보내기 규칙, 검토 절차 등을 기존의 프로세스와 유사한 방식으로 처리합니다.
- 에이전트들은 잘 설명된 도구를 선택하여, 처음부터 전체 워크플로우를 다시 만들어내는 대신, 검증된 근거를 바탕으로 작업을 수행합니다.

이를 통해 반복적인 코드 생성이 줄어들고, 스튜디오는 프로젝트, 부서, 또는 제작 단계에 따라 다양한 기능을 제공할 수 있습니다. 또한, 이 방식으로 인해 제어 플랫폼을 별도로 구축할 필요가 없습니다.

## 실패의 증거를 보관해 두세요.

진단은 `request_id`, 사용된 도구와 인수들, 선택된 DCC 인스턴스, 그리고 관찰된 결과로 시작됩니다. Gateway와 CLI는 건강 상태, 로그, 추적 데이터, 통계 정보, 그리고 구조화된 피드백을 제공합니다.

이것은 구체적인 루프를 만들어냅니다.

1. 실제 호스트에서 발생하는 오류를 재현합니다.
2. 코어가, 어댑터인지, 아니면 스킬인지를 식별합니다.
3. 그 경계에서 가장 작은 수정을 해야 합니다.
4. 동일한 호출을 다시 확인하는 것입니다.
5. 증거를 잘 보관해두어야 합니다. 그렇게 하면 다음 단계의 개선은 추측이 아니라, 실제 경험을 바탕으로 이루어질 수 있습니다.

## 알려진 한계들

DCC-MCP는 모든 창의적인 활용 사례가 동일하다고 주장하지 않습니다.

- 네이티브 스킬과 API를 사용하는 것이, DCC-CUA/UI Control을 사용하는 것보다 더 선호됩니다. 왜냐하면 DCC-CUA/UI Control을 사용할 경우, 정확한 프로세스와 창을 연결해야 하기 때문입니다.
- Core는 호스트에 특화된 파이프라인 세미나를 가지고 있지 않습니다.
- 호스트가 트랜잭션 API를 제공하지 않는 경우, 어댑터는 안전한 롤백을 보장할 수 없습니다.
- 마켓플레이스 패키지는 기존의 프레임워크를 확장하는 역할을 합니다. 즉, Core나 어댑터의 결함을 숨기지 않습니다.
- 이 프로젝트는 에이전트들을 위한 인프라를 제공합니다. 어떤 에이전트나 모델을 사용해야 하는지는 명시되어 있지 않습니다.

## 아직도 인간의 판단에 의존해야 하는 부분들이 있습니다.

많은 생산 작업들은 표준화되고, 검증된 형태로 자동화될 수 있습니다. 하지만 미적 감각, 예술적 디자인, 구성, 타이밍, 스타일과 같은 요소들은 여전히 안정적인 형태로 표현하기가 어렵습니다. DCC-MCP는 인프라만으로 이러한 문제들을 해결할 수 있다고 주장하지 않습니다.

DCC-MCP는 반복적인 작업들을 처리하며, 에이전트들이 실제 도구들을 제어할 수 있도록 해줍니다. 더 나은 인식력, 추론 능력, 그리고 창의적인 판단력을 활용하기 위해서는, 모든 DCC 통합 작업을 다시 구축하지 않고도 동일한 도구들을 사용할 수 있습니다.
