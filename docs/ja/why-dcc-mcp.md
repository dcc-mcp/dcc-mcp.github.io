# DCC-MCP の設計と導入の考え方

## DCC-MCPとは何ですか？

DCC-MCPは、AIエージェントを創造的なソフトウェアに接続するためのオープンソースのツールセットです。AIエージェントとは、さまざまなツールを呼び出して作業を行うことができるAIアシスタントのことです。DCCとはデジタルコンテンツの作成を意味します。利用可能なアプリケーションには、Maya、Blender、Houdini、Photoshopなどがあります。

エージェントや自動化システムは、これらのツールを利用して、モデリング、素材の処理、アニメーションの生成、レンダリングなどを行うことができます。タイプされたツールは、そのパラメータや型、そして得られる結果を定義しています。そうすることで、その実行結果を確認し、検証することができます。

MCP（Model Context Protocol）、REST API、そして`dcc-mcp-cli`は、ツールの検出、検証、インスタンスの選択、セキュリティポリシーの設定、結果の確認といった機能を共有しています。Coreは、このような共通のインフラストラクチャを提供しています。アダプターは、各アプリケーションを接続し、Skillsは再利用可能なワークフローガイドを提供します。

DCC-MCPは、実際のDCCアプリケーション間でのアダプターの処理から生まれました。スレッドの親子関係、インスタンスの選択、ライフサイクル、ディスカバリー、診断といった機能は、さまざまなホストで繰り返し発生していました。これらの問題が再発した後に、私たちは共有コントラクトを導入しました。

## 生産プロセスから始めましょう。

エージェントは、与えられたプロセスを使います。そのプロセスを、チームのために定義することはありません。

> 標準化された生産を行う → その標準をワークフローに変換する → ワークフローをツールとしてまとめる → エージェントがそのツールを操作できるようにする

名前、入力値、出力値、チェック項目、所有権、および受け入れ基準を定義します。これらを一連の反復可能なワークフローにまとめ、そのワークフローをタイプ化されたツールとして提供します。このツールは、人間やスクリプト、CIツール、またはエージェントによって呼び出すことができます。

## なぜ、直接スクリプトを使用するとスケーリングができなくなるのか？

モデルに、`mayapy`や`hython`、またはBlender用のPythonスクリプトを書いてもらうことは、探索的な目的には役立ちます。しかし、繰り返し実施される作業によって、以下のような限界が明らかになりました。

- このモデルは、各ターンごとに同じようなコードを再生成しますが、その結果は毎回異なります。
- DCC APIでは、通常、メインスレッドでの実行が必要であり、また、アプリケーション固有の準備状態の確認も必要です。
- いくつかのオープンなシーンやアプリケーションインスタンスがあると、実行対象が不明確になってしまいます。
- 長期的な作業には、進捗の管理、中断の処理、チェックポイントの設定、そして復旧処理が必要です。
- 成功したプロセスの終了が、意図されたシーンや文書が変更されたことを意味するわけではありません。
- このような失敗は、タイプ入力やリクエストID、ログ、トレース情報がないと再現するのが難しいです。

これらの問題は、さまざまなアダプターで発生していました。ですから、これらは共有インフラストラクチャー内で処理されるべきものでした。

## 問題点と、それらによって生じる契約の問題点

| 繰り返す問題 | 私たちが学んだこと | DCC-MCPの応答 |
| --- | --- | --- |
| モデルは、各ターンごとにタスクのロジックを再構築します。 | パイプライン上の知識は、モデルやプロンプトが変わっても保持されるべきです。 | バージョン管理されたスキル、タイプされたスキーマ、検証機能、そして再利用可能なツールがあります。 |
| すべてのアダプターは、輸送処理やライフサイクルに関するコードを再構築します。 | ホストの統合には、共通の契約が必要です。 | コアランタイム、ゲートウェイ、CLI、そしてシンクレウス独自のアダプター |
| DCC APIには、スレッドや準備状況に関する制約があります。 | 一般的なプロセスの実行だけでは不十分です。 | メインスレッドの派遣、準備状況、インスタンスのルーティング、およびホストでの実行に関するブリッジ |
| 大きなツールカタログは、コンテキストを消費し、選択を混乱させてしまいます。 | エージェントは、タスクに必要な情報のみを把握すればよいのです。 | `search -> load/describe -> call`の発見 |
| 創造的な作業は、遅く進んだり、部分的にしか完了しなかったりすることがあります。 | コールには、戻り値だけでなく、ライフサイクルに関するセマンティクスも必要です。 | 非同期のジョブ、進捗状況、キャンセル処理、チェックポイント、そしてアーティファクトの引継ぎについて |
| 道具の使用は、まるでブラックボックスのようなものになってしまいます。 | 制作チームは、自分たちが確認できるような証拠が必要です。 | リクエストのID、ポリシー、アドバイザリレコード、ログ、トレース、メトリクス、ヘルス状態、および再実行に関する情報 |
| 既存のツールの中には、利用可能なAPIが存在しないものもあります。 | UI自動化は、基盤ではなく、代替手段に過ぎません。 | DCC-CUA / 正確なプロセスとウィンドウにバインドされたUIコントロールで、範囲指定された操作、ポリシーチェック、および`snapshot -> find -> act -> wait -> verify`が可能です。 |
| 有用なワークフローは、人々やプロジェクトの間を移動しなければなりません。 | スクリプトフォルダというのは、ディストリビューションのモデルではありません。 | マーケットプレイス用のパッケージ、不変のソース参照、ホットリロード、およびプロジェクト/チームのスコープ |

## どの人が、どのようなものの所有権を持っているのか？

このシステムは、共有サービスと、ホストごとの特有の動作を区別しています。

| レイヤー | 責任 |
| --- | --- |
| エージェントインターフェース | MCPおよびRESTエンドポイント、CLIコマンドの入力、スキーマ、リソース、プロンプト、そして構造化された結果 |
| コントロールプレーン | ゲートウェイのディスカバリー、ルーティング、ポリシーのチェック、ライフサイクルの管理、可観測性の確保、そして複数のインスタンス間の連携処理 |
| DCC実行時間 | メインスレッドの派遣、準備状況、ジョブの処理、キャンセル、チェックポイント、そしてホストに安全に実行される処理 |
| アダプター | インストール、互換性、ホストのAPI、そして各DCCリポジトリが管理するアプリケーション固有の動作については、それぞれのDCCリポジトリが担当しています。 |
| スキル | ワークフローに関する知識の確認、論理的な議論の検証、ワークフローの各ステップの確認、そしてプロジェクトやチームの規則や慣習の確認を行います。 |

[コアアーキテクチャのドキュメント](https://dcc-mcp.github.io/dcc-mcp-core/guide/architecture)は、現在のコントラクトの正確な情報源です。ホストごとのインストール方法や互換性、トラブルシューティングについては、各アダプターリポジトリに記載されています。

## CLI、MCP、RESTは、共通の実装を共有しています。

共有サービスコードや、テキストで記述されたREST/OpenAPIコントラクトが実装の仕方です。`dcc-mcp-cli`はGatewayのREST APIを呼び出します。MCP自体はシンプルです。`search`、`describe`、`load_skill`、`call`といった機能は、MCP専用のクライアントに対して同じワークフローを提供します。どちらのルートも、同じディスカバリー機能、検証機能、ルーティング機能、ポリシー機能、呼び出し機能を使用しています。

| 消費者 | 好ましい表面 | AIエージェントが必要です。 |
| --- | --- | --- |
| アーティスト、TDs、オペレーター、シェルスクリプト、そしてCI | タイプされたCLIまたはREST | いいえ。 |
| スタジオの自動化機能や、カスタムアプリケーションについて | 生成されたOpenAPIクライアントを使って、休息を取ることができます。 | いいえ。 |
| MCPのみを搭載したAI開発環境やアシスタント | 最小限のMCPワークフロー | はい。 |
| スマートなワークフロー管理システムや、クラウドベースのオーケストレーション機能 | REST/OpenAPIの統合；エージェントが参加する場合には、MCPが利用可能です。 | いいえ。 |

パイプラインは、直接RESTを呼び出したり、`/v1/openapi.json`からクライアントを生成したり、CIや運用時にCLIを使用することもできます。エージェントも、Thin MCPインターフェースを通じて同じ機能を利用できます。

既存のOpenAPI 3.xサービスも、MCPツールとして利用することができます。これは、通常のRESTサービスとして機能し、AIを活用して再構築する必要はありません。

## まずは、既存のプロトコルを利用してください。

MCPは、業界標準のエージェントエントリポイントです。そのため、DCC-MCPは独自のプロトコルを開発するのではなく、MCPを利用しています。REST、Python、C++、HTTP、コマンドポート、ネイティブプラグイン、そして公式なベンダーのツールセットなども、同じコントロールプレーンを通じて利用できます。

DCC-MCPは、エージェントやDCC API、ベンダーの統合機能を代替するものではありません。ベンダが利用可能なネイティブなMCP機能を提供している場合、そのアダプターはその名前やスキーマを保持します。DCC-MCPは、その周囲の共有されたディスカバリー機能、ルーティング機能、セキュリティ機能、ライフサイクル機能、配布機能、診断機能を提供します。

## スキルストアのワークフローに関する知識

スキルとは、テストされたワークフローを、バージョン管理された、形式化された、そして配布可能な形で提供するものです。

所有権の境界は、以下の通りです：

- コアとアダプターは、接続性、スレッドの安定性、ルーティング、ポリシー、および可観測性の面で独自の機能を持っています。
- TDsとTAsは、プロジェクトの命名、シーンのチェック、アセットの準備、公開のタイミング、エクスポートのルール、レビューの手続きなどを、既存のパイプラインコードに近い形で実行しています。
- エージェントは、十分に説明されているツールを選び、それに基づいて検証された論拠を提供するのです。つまり、全く新しいワークフローを作り出すのではなく、既存のツールを利用するのです。

これにより、コードの繰り返し生成が避けられ、スタジオは、プロジェクトや部門、制作段階に応じて、異なる機能を提供することができます。また、コントロールプレーンを分離することなく実現できます。

## 失敗の証拠を保持しておきましょう。

診断は、`request_id`、使用されているツールや引数、選択されたDCCインスタンス、そして観測された結果から始まります。GatewayやCLIでは、ヘルス状態、ログ、トレース情報、統計データ、そして構造化されたフィードバックが提供されます。

これにより、具体的なループが形成されます。

1. 実際のホストに対して、その障害を再現する。
2. それがコアであるか、アダプターであるか、それともスキルであるかを識別する。
3. その境界で、できるだけ小さな修正を行うことです。
4. 同じ通話を再び有効化する。
5. 証拠を保持しておくことで、次の改善は、推測ではなく、実際の経験に基づいて行われるようになります。

## 既知の限界

DCC-MCPは、すべての創造的なアプリケーションが同じになるとは主張していません。

- ネイティブなスキルやAPIの使用が、DCC-CUA/UI Controlよりも望ましいです。なぜなら、DCC-CUA/UI Controlでは、正確なプロセスやウィンドウを指定する必要があるからです。
- Coreには、ホスト固有のパイプラインに関するセマンティクスはありません。
- ホストがトランザクションAPIを提供していない場合、アダプターは安全なロールバックを保証することはできません。
- マーケットプレイス用のパッケージは、そのフレームワークを拡張するものです。つまり、Coreやアダプターの欠陥を隠すことはありません。
- このプロジェクトは、エージェントに必要なインフラを提供するものです。どのエージェントやモデルを使用すべきかは、このプロジェクトでは定められていません。

## まだ、人間の判断に委ねられている部分があります。

多くの生産作業は、標準化され、検証され、自動化されることができます。しかし、美的判断やアートディレクション、コンポозション、タイミング、スタイルといった要素を、安定した契約として表現するのは依然として難しいです。DCC-MCPは、インフラだけでこれらの問題を解決できると主張していません。

DCC-MCPは、繰り返し行われる作業を処理し、エージェントが実際のツールを操作できるようにしています。より良い認識力、推論能力、創造的な判断能力を活用するためには、同じツールを使用することができます。そうすることで、各DCCの統合処理を毎回行う必要はありません。
